# ADR: Стратегия шардирования для коллекции orders

## Контекст

Нужно чтобы создание заказа происходило быстро, быстро выполнять заказы в корзине когда заходит новый пользователь

---

## Решения

### 1. Выбранные поля для таблицы orders

`_id integer [primary key]` - для хранения идентификаторв

`clinet_id integer` - идентификатор клиента

`created_at timestamp` - время создания заказа

`items json  [note: '{ product_id, quantity }']` - список продуктов. Для простоты текущей реализации принято решение хранить список продуктов как JSON поле

`status varchar` - статус заказа

`total_sum decimal` - сумма заказа

`region varchar` - гео-регион

### 2. Кандидаты для шард ключей таблицы orders

**Поле:** `client_id`

**Стратегия шардирования:** Хэшированное шардирование

**Приемущества**: 
- Все заказы одного клиента хранятся физически в одной БД

**Недостатки**
- В случае необходимости администратором получать список заказов по другим параметрам, запрос будет выполняться медленнее, так как данные физически в разных БД

**Обоснование решения**:
- Шардирование по полю client_id позволит хранить все заказы в одной физической БД, что обеспечит быстрый доступ к заказам одного пользователя
- В требованиях обеспечить быстроту работы с коллекцией именно для клиентов. Любые операции со своими заказами будут быстрыми для клиента


**Альтернативы**:
- Поле `region`
    - **Приемущества**:
        - Данные распределеные по регионам. Операции в рамках одного региона будут быстрее
    - **Недостатки**:
      - Если клиент делает заказы из разных регионов - получение списка заказов по клиенту будет занимать большее колчиество времени

### 3. MongoDB команды для шардирования коллекции orders

```javascript
mongosh --host mongos:27017

sh.enableSharding("somedb")

db.orders.createIndex({ client_id: "hashed" })

sh.shardCollection("somedb.orders", { client_id: "hashed" })

db.orders.createIndex({ client_id: 1, created_at: -1 })
db.orders.createIndex({ status: 1 })         


sh.status()

db.orders.getShardDistribution()
```

# ADR: Стратегия шардирования для коллекции products

## Контекст

Необходимо обеспечить быстрый поиск товаров по категориям и фильтрацию по диапазону цен, а также быстрое отображение страницы товара.

---

## Решения

### 1. Выбранные поля для таблицы products

`_id integer [primary key]` - уникальный идентификатор товара

`name varchar` - наименование товара

`category varchar` - категория товара

`price decimal` - цена товара

`attributes json` - дополнительные атрибуты (цвет, размер и т.д.)

### 2. Кандидаты для шард ключей таблицы products

**Поле:** `_id` (хэшированное)

**Стратегия шардирования:** Хэшированное шардирование

**Преимущества**: 
- Равномерное распределение данных между шардами
- Быстрый доступ к конкретному товару по идентификатору (страница товара)
- Отсутствие "горячих" шардов при высокой нагрузке

**Недостатки**:
- Запросы по категории или диапазону цен будут scatter-gather (распределенные по всем шардам)

**Обоснование решения**:
- Коллекция products относительно статична (товары редко добавляются/удаляются массово)
- Для оптимизации поиска по категориям и ценам используются **индексы**: `{ category: 1, price: 1 }`
- Страница товара - одна из самых частых операций, хэширование по `_id` обеспечивает максимальную скорость
- При использовании кэширования (Redis) нагрузка на scatter-gather запросы существенно снижается

**Альтернативы**:
- Поле `category`
    - **Преимущества**:
        - Запросы по категории будут локальны для одного шарда
    - **Недостатки**:
        - Неравномерное распределение данных (популярные категории создадут "горячие" шарды)
        - Запросы по `_id` будут требовать обращения к роутеру

### 3. MongoDB команды для шардирования коллекции products

```javascript
mongosh --host mongos:27017

sh.enableSharding("somedb")

db.products.createIndex({ _id: "hashed" })

sh.shardCollection("somedb.products", { _id: "hashed" })

db.products.createIndex({ category: 1, price: 1 })
```

# ADR: Стратегия шардирования для коллекции product_stock

## Контекст

Необходимо обеспечить быстрое обновление остатков при покупках и быстрое списание товаров при создании заказа. Остатки хранятся отдельно по геозонам.

---

## Решения

Решено добавить новую таблицу product_stock для быстроты обновления количество товаров на складе

### 1. Выбранные поля для таблицы product_stock

`product_id integer` - идентификатор товара (ссылка на products._id)

`region varchar` - геозона

`stock integer` - количество товара на складе в данной геозоне

### 2. Кандидаты для шард ключей таблицы product_stock

**Поле:** Составной ключ `{ region: 1, product_id: 1 }`

**Стратегия шардирования:** диапазоноек шардирование

**Преимущества**: 
- Все остатки одного региона хранятся на одном шарде - операции списания при заказе локальны
- При создании заказа (который привязан к региону) запрос на обновление остатков идет на один шард
- Возможность получить все остатки региона одним запросом (для аналитики склада)

**Недостатки**:
- Запрос остатков конкретного товара по всем регионам будет scatter-gather

**Обоснование решения**:
- Основная операция - списание остатков при создании заказа. Заказ всегда привязан к конкретному региону
- При шардировании по `{ region, product_id }` операция списания остатков будет targeted (на один шард)
- Это критично когда нагрузка на обновление остатков максимальна

**Альтернативы**:
- Поле `product_id` (хэшированное)
    - **Преимущества**:
        - Все остатки товара по всем регионам на одном шарде
        - Равномерное распределение
    - **Недостатки**:
        - При создании заказа с несколькими товарами - обращение к нескольким шардам
        - Менее эффективно для массовых операций в рамках одного региона

### 3. MongoDB команды для шардирования коллекции product_stock

```javascript
mongosh --host mongos:27017

sh.enableSharding("somedb")

db.product_stock.createIndex({ region: 1, product_id: 1 })

sh.shardCollection("somedb.product_stock", { region: 1, product_id: 1 })

db.product_stock.createIndex({ product_id: 1 })

sh.splitAt("somedb.product_stock", { region: "moscow", product_id: MinKey })
sh.splitAt("somedb.product_stock", { region: "rostov", product_id: MinKey })
sh.splitAt("somedb.product_stock", { region: "ekb", product_id: MinKey })
```

# ADR: Стратегия шардирования для коллекции carts

## Контекст

Необходимо обеспечить быстрое создание корзины при заходе пользователя/гостя, быстрое получение активной корзины и эффективное слияние гостевой корзины с пользовательской при авторизации.

---

## Решения

### 1. Выбранные поля для таблицы carts

`_id integer [primary key]` - уникальный идентификатор корзины

`user_id integer` - идентификатор пользователя (null для гостей)

`session_id varchar` - идентификатор сессии (для гостей и связи с пользователем)

`items json [note: '{ product_id, quantity }']` - список товаров в корзине

`status varchar` - статус корзины ("active", "ordered", "abandoned")

`created_at timestamp` - время создания

`updated_at timestamp` - время последнего обновления

`expires_at timestamp` - время автоматического удаления (TTL)

### 2. Кандидаты для шард ключей таблицы carts

**Поле:** Составной ключ `{ session_id: "hashed" }`

**Стратегия шардирования:** Хэшированное шардирование по session_id

**Преимущества**: 
- Session_id присутствует для всех корзин (и гостевых, и пользовательских)
- Равномерное распределение данных между шардами
- Основные операции (получение/обновление корзины) по session_id будут targeted

**Недостатки**:
- При слиянии корзин (гостевая - пользовательская) возможно обращение к разным шардам
- Запрос корзины только по user_id будет scatter-gather

**Обоснование решения**:
- Session_id - универсальный идентификатор, присутствующий во всех сценариях
- Даже авторизованные пользователи имеют session_id, что позволяет быстро находить корзину
- Для оптимизации запросов по user_id создается **индекс**: `{ user_id: 1, status: 1 }`
- Операция слияния корзин происходит редко (только при логине), поэтому scatter-gather допустим
- TTL-индекс на `expires_at` обеспечивает автоматическую очистку старых корзин

**Альтернативы**:
- Поле `user_id`
    - **Преимущества**:
        - Все корзины пользователя на одном шарде
        - Быстрое слияние корзин
    - **Недостатки**:
        - Гостевые корзины имеют `user_id = null` - все они попадут на один шард (критический дисбаланс)
        - Не подходит для системы с большим количеством гостей

- Поле `_id` (хэшированное)
    - **Преимущества**:
        - Равномерное распределение
    - **Недостатки**:
        - Основные запросы идут по session_id или user_id, а не по _id
        - Все операции будут scatter-gather

### 3. MongoDB команды для шардирования коллекции carts

```javascript
mongosh --host mongos:27017

sh.enableSharding("somedb")

db.carts.createIndex({ session_id: "hashed" })

sh.shardCollection("somedb.carts", { session_id: "hashed" })

db.carts.createIndex({ user_id: 1, status: 1 })

db.carts.createIndex({ expires_at: 1 }, { expireAfterSeconds: 0 })

db.carts.createIndex({ session_id: 1, status: 1 })
```
